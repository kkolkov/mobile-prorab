# Распознавание чеков в новом расходе

В WEB и Expo в форме «Новый расход» есть «Распознать чек». Пользователь выбирает
одно фото. Приложение показывает предложенные название, сумму и дату отдельно:
ввод не меняется до нажатия «Заполнить из чека». Категория и этап не меняются.
Расход и фотография сохраняются только по обычной кнопке «Сохранить».

После сохранения чек открывается через «Посмотреть чек» в истории расходов
финансового трекера. Редактирование суммы/названия сохраняет фото, удаление расхода
удаляет его фото. Сеть и конфликт версии не стирают локальный ввод. Распознавание
само не создаёт расход, не меняет бюджет и не завершает этап.

## Настройка

- Бесплатный ключ: https://ocr.space/ocrapi
- На backend задать `OCR_SPACE_API_KEY`.
- Локально: корневой `.env.local`, строка `OCR_SPACE_API_KEY=...`; перезапустить backend.
  Spring читает этот файл при запуске из корня или backend/. Файл исключён из Git.
- Render: сервис mobile-prorab → Environment → Add Environment Variable →
  `OCR_SPACE_API_KEY`; Save, rebuild, and deploy. Ключ не передаётся клиентам.
- Без ключа сервис возвращает понятную ошибку; фото можно прикрепить и сохранить
  с вручную введёнными данными. Платный резервный провайдер не подключён.

## Как работает

POST `/api/projects/{projectId}/execution/receipt/recognize`, body `{dataUrl}`.
Требует авторизацию владельца. Ответ: `{title, amount, date, warnings}`; неизвестные
и неоднозначные значения null. OCR.space вызывается сервером по HTTPS, ключ только
в заголовке. Engine 2, язык auto, isTable=true. Внешний запрос ограничен 10 секундами;
повторная отправка только по явному нажатию. Текст и фото не логируются.

Изображение нормализуется в JPEG без метаданных, до 3200px по стороне. Для OCR
сервер проверяет размер до 1 000 000 байт. Если сжатия недостаточно, предлагается
обрезать лишний фон. Это отдельный режим: фото завершения этапов остаются до 1600px.

Парсер ищет только явно подписанный итог (ИТОГ/ИТОГО, К ОПЛАТЕ, СУММА РАСЧЁТА,
TOTAL). НДС, сдача и переданные наличные не служат заменой итогу. Несколько разных
итогов или дат требуют ручного ввода. Возврат не превращается в положительный расход.
Название предлагается при распознанных ООО/ИП/АО/ПАО/МАГАЗИН в начале чека.
Чек с товарными строками считается одним расходом; категоризация товаров не реализована.

До сохранения OCR не пишет данные проекта/фото в БД. Команда `expense` принимает
необязательный `receipt: {dataUrl}`. Фото хранится в уже существующей таблице
stage_photos, ссылка receiptPhotoId — в JSON расхода. Доступ к файлу только владельцу,
через существующий защищённый endpoint. Сохранение атомарное; повтор того же расхода
с тем же чеком после потерянного ответа не дублирует затраты.

## Ограничения и проверка

Документация OCR.space на 22.10.2026: Free — 25 000 запросов/месяц, до 500/день/IP,
файлы до 1 МБ, без SLA. Локальная защита процесса: 2 параллельных запроса,
5/минуту на аккаунт, 400/день на процесс. Счётчики обнуляются при рестарте; это защита
от случайных повторов, а не распределённый счётчик тарифа. Лимит провайдера остаётся
общим для исходящего IP. Источник: https://ocr.space/ocrapi

Проверен настоящий API на искусственном русском чеке: итог 1234.50, дата 22.10.2025,
магазин распознаны; расход не создан. Автотесты парсера используют искусственные
примеры, транспортные тесты — локальный HTTP-сервер, браузерные сценарии — подставной
ответ OCR и реальный backend/PostgreSQL. Эти тесты не доказывают качество на реальных
фотографиях. Для оценки нужны 20–30 реальных чеков разных магазинов: точное совпадение
итога/даты, частота ручных исправлений, работа с бликами, поворотами и длинными чеками.
Физические iOS/Android отдельно не проверены. Render/APK для этой функции не обновлены.
