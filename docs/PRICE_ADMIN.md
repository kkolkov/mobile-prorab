# Минимальная админка цен

Простая пошаговая инструкция с примером: `PRICE_ADMIN_QUICKSTART.md`.

Адрес: `/porabadmin` (именно такое написание согласовано пользователем).
Локально: http://localhost:8080/porabadmin; после отдельной выкладки — тот же путь на Render.
Авторизации нет по явному запросу пользователя. Исключение относится только к API
справочника `/api/porabadmin/prices`; проекты и аккаунты остаются закрытыми.

## Что можно менять

- Цена комплексной позиции за указанную единицу: работа + материалы.
- Доля черновых материалов и доля работы, в процентах. Остаток — чистовые материалы/оснащение.
- Источник (ссылка или название прайса, город, состав цены), дата и отметка проверки цены.
- Удаление строки с подтверждением. Удалённую обязательную позицию можно вернуть,
  задав значения заново; скрытые стартовые цены не подставляются.

Код, название и единица фиксированы: они связаны с калькулятором. Произвольные новые
коды пока не добавляются — движок не знал бы, когда их применять. Справочник требует
10 ставок; при удалении любой новый расчёт недоступен до восстановления. Старые
сметы, графики и расходы остаются. UI показывает список отсутствующих ставок.

Сумма долей ≤100%, цена положительная с двумя знаками, дата не будущая, источник
обязателен. При изменении полей форма сбрасывает отметку проверки. Проверка —
утверждение администратора об источнике цены, а не сертификат точности всей сметы.

Изменения сохраняются сразу в PostgreSQL. Конфликт версий возвращает 409; форма
сохраняет ввод и предлагает явно загрузить актуальную версию. Отказ сети также не
очищает ввод. Flyway V11 добавляет `version` и `verified` со значениями 0/false.

Новые расчёты используют новый справочник; старые снимки не переписываются.
Для существующего проекта: уточнение → повторить расчёт → сравнить → применить.
Для финансов затем отдельно обновить план из применённой сметы. Начатый график
автоматически не сдвигается.

В пояснениях расчёта указано, остались ли непроверенные цены или все цены отмечены
администратором как проверенные. Геометрия и коэффициенты продолжают описываться
как допущения; `demonstration=true` сохранён, поскольку модель ещё не откалибрована.

# Как заменить допущения проверенными данными

## Что подготовить владельцу продукта

1. Выбрать один рынок для начала: город, дата/период цен, тип ремонта. Не смешивать
   подрядчиков и цены с разным составом работ без пояснений.
2. Собрать исходные прайсы: материал, расход на единицу, цена работы, что включено
   (подготовка, расходники, доставка, налоги). Комплексная ставка должна учитывать
   каждый компонент ровно один раз. Например, упаковку ламината пересчитать в ₽/м²,
   добавить подложку и укладку; подготовку не добавлять повторно, если она уже отдельной строкой.
3. Собрать 5–10 подробных смет с обмерами для первого разбора. Это стартовый набор,
   а не доказательство точности. По законченным ремонтам добавить фактические расходы
   и изменения объёма работ. Плановую смету подрядчика не выдавать за фактическую стоимость.
4. Для каждого объекта: тип комнаты, площадь пола/потолка, периметр, высота,
   площадь дверных/оконных проёмов, площадь облицовки, количество дверей, электроточек,
   сантехнических выводов и приборов; площади демонтажа/подготовки, состав кухни/техники.
5. Сравнить отдельно ошибки объёмов и ставок, затем итог. Выделить другие квартиры
   для проверки после настройки: не подбирать коэффициенты по той же выборке,
   на которой заявляем результат. Заранее согласовать допустимое отклонение и
   сообщать фактически полученное, включая плохие случаи.

## Что где регулируется сейчас и что нужно доработать

|---|---|---|

| Стены: 4 × √S × h × 0,85 | `UnitPriceCalculator.walls` | Добавить в UI/API периметр и проёмы или непосредственно измеренную площадь стен; без обмеров оставить маркированное приближение |
| Материалы ×1 / 1,2 / 1,6 / 2,2 | `UnitPriceCalculator.material` | Предпочтительно отдельные ставки для ламината, плитки, покраски и т. п.; сравнивать одинаковый состав работ |
| Класс ×1 / 1,3 / 1,7 | `UnitPriceCalculator.Ledger` | Подтвердить сопоставимыми комплектами материалов/работ или заменить ставками по классам; не умножать второй раз уже выбранную дорогую позицию |
| Подготовка/демонтаж 50%, инженерные точки | `UnitPriceCalculator` | Добавить фактические объёмы/количество; проверить нормы для случаев без данных |
| Двери как доля мебели, приборы как коэффициенты | `UnitPriceCalculator` | Отдельные расценки дверей, приборов и монтажа вместо условных эквивалентов |
| Срок и пауза | `TimePlanner` | Данные о реальной длительности этапов, составе бригад и технологии; цены сами по себе срок не подтверждают |

Проверяемый коэффициент — отношение цен двух сопоставимых решений, например
K = комплексная цена плитки за м² / комплексная цена базового пола за м².
Нужны несколько наблюдений, одинаковые единицы и состав работ. Одна случайная
котировка не подтверждает универсальный коэффициент. Отдельные ставки обычно
понятнее и проще проверяются, чем универсальные множители.

Для оценки точности можно считать по каждому объекту:
ошибка, % = (расчёт − сопоставимая фактическая стоимость) / фактическая стоимость × 100.
Отдельно показать среднюю абсолютную ошибку, направление смещения и диапазон ошибок.
Исключения из состава сметы и изменения проекта фиксировать явно, а не вычитать
неудобные случаи после проверки. Точность бюджета не означает точность срока.

Приоритет: реальные ставки → отдельные цены дверей/приборов/материалов → реальные
объёмы стен и инженерии → проверка на других объектах. Просто перенос коэффициентов
из Java в админку сделает их редактируемыми, но не подтвердит их достоверность.
