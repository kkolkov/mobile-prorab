# Дополнения интерфейса и проекта — 21 октября 2026

Основание: пользовательский `additional_work.docx`. Эти согласованные изменения
уточняют прежние требования; исходная постановка не переписана. Реализованы в вебе
и Expo, серверные изменения общие для обоих клиентов.

1. Под паролем видна подсказка «От 8 до 128 символов».
2. В графике у незавершённого этапа есть «Изменить дату начала» и «Продлить этап».
   Новая дата может быть раньше текущей. Длительности выбранного и последующих
   этапов сохраняются; предыдущие и завершённые этапы не меняются. Начало после
   предыдущего этапа обязательно. Перенос первого этапа меняет начало проекта.
   Первоначальные даты, расходы и финансовый план сохраняются, перенос записывается
   в историю. Новый API: POST `/api/projects/{id}/execution/reschedule`, поля
   `version`, `taskId`, `date`.
3. В уточнении под «Общая отделка» добавлена перепланировка Да/Нет. Начальное
   значение берётся из проекта, сохранение обновляет проект. Для старого JSON без
   поля клиенты используют значение проекта. Отдельной цены перепланировки модель
   по-прежнему не содержит — это отмечено в допущениях сметы.
4. Первое подтверждение раздела даёт «Данные указаны», даже без изменения значений.
   Изменение уже подтверждённого раздела после успешного сохранения даёт
   «Данные указаны и обновлены». В JSON уточнения хранится `updatedSections`.
   Возврат без сохранения не меняет сохранённый статус; локальный черновик остаётся
   с отметкой несохранённого ввода. Сохранение без изменений не увеличивает версию.
5. В помещениях убран отдельный счётчик жилых комнат; добавление — через «+ Добавить».
   Разрешено удалить последнюю жилую комнату; заполненные помещения требуют прежнего
   подтверждения удаления.
6. «Полностью обустроенная» видна, но недоступна для нового выбора в обоих клиентах.
   Старые значения, API-коды и существующий расчёт этой категории сохранены.
7. Название помещения необязательно. Пустое получает название типа и следующий
   номер среди помещений того же типа (после наибольшего имеющегося номера,
   не меньше количества существующих помещений + 1). Свой текст сохраняется.
   Клиенты показывают имя сразу после «Готово», сервер тоже обрабатывает пустое имя.
8. В создании/возврате к «Об объекте»: 5–9999 м² включительно, один десятичный знак.
   Диапазон проверяется клиентами и сервером.
9. В мастере комнаты и санузлы: 0–20. При обоих нулях нужно подтвердить чекбокс
   «Ремонт будет в других помещениях?». Подтверждение хранится в `otherRoomsRepair`.
   Кухня остаётся в расчёте, остаток площади распределяется прежним алгоритмом;
   помещения с нулевым количеством не создаются и не начисляются как комнаты/санузлы.
10. Повтор расчёта действительно вызывает сервер. Если расчёт снова не удался,
    появляется отдельное объяснение и возможность исправить параметры или открыть
    уточнение. Повтор запроса сам по себе не исправляет недостаток площади для
    выбранного состава помещений. Проект и старая оценка не теряются.
11. Под «Перейти в проект» доступно удаление с подтверждением Да/Нет.
12. Такое же удаление доступно из карточек «Мои проекты».

## Данные и удаление

Flyway V9 добавляет флаг ремонта других помещений. V10 разрешает ноль комнат и
добавляет ON DELETE CASCADE для уточнения и execution. Java-миграция находит имена
прежних ограничений через metadata: PostgreSQL и тестовая H2 назначали разные имена.
Исторические миграции V1–V8 не менялись.

POST `/api/projects/{id}/delete?version=N` проверяет владельца и версию, блокирует
строку проекта и удаляет проект вместе с уточнениями, снимками сметы, графиком,
расходами и историей execution в одной транзакции. Чужой проект: 404, старая версия:
409. Поздний результат расчёта удалённого проекта игнорируется. Учётная запись,
история назначения A/B и доступ аккаунта не сбрасываются.

Render и APK в рамках этой задачи не обновлялись.
